# Feature Specification: Internal Cluster Vault

**Feature Branch**: `main` (existing branch; no branch-creation hook configured)

**Created**: 2026-10-02

**Status**: Ready for planning; constitutional reconciliation completed (Constitution v1.3.0)

**Input**: User description: "I want to build our own internal cluster vault system into our kubernetes system." Clarified intent: the vault performs authorized operations using credentials internally and returns results; application nodes and project pods must not receive backend credentials, including in memory.

## Clarifications

### Session 2026-10-03

- Q: Does “our own” mean operating an established vault product or developing a custom vault service? → A: Self-host an established vault. The organization owns deployment, data, access policies, and cluster integration; product selection belongs to planning. Developing a custom vault security engine is out of scope.
- Q: How should applications and nodes use managed credentials? → A: Request a complete authorized operation from the vault service and receive its result. Backend credentials must remain inside trusted execution; they must not be returned to callers or copied into their Kubernetes datastore, files, environment variables, or memory. This replaces the earlier secret-delivery design.
- Q: What integration changes are acceptable for this model, including private GHCR image pulls? → A: Provide service-specific operation integrations. Cluster and container-runtime configuration, deployment configuration, and project application code may need changes depending on the operation. Modifying Kubernetes source code is not an assumed requirement. A GHCR integration must return image contents rather than registry credentials.

- Q: May the vault use separate, isolated helper services to perform operations such as pulling a private GHCR image? → A: Both arrangements represent the same requirement: one protected logical service performs the work and returns only results. Internal process decomposition belongs to planning; backend credentials must remain outside application nodes and project pods.
- Q: May a Kubernetes node or application hold a temporary identity token to prove who it is when asking the protected service to perform work? → A: Yes. Start with short-lived caller identity tokens and narrowly scoped permissions. The service verifies identity and current authorization on each request, keeps backend credentials internally, returns only permitted results, and records audit events without token or credential values.

- Q: Which operations must the first release support before it is complete? → A: Include database access and all other existing platform and project backend credential uses in this spec now, alongside private GHCR image pulls. Every inventoried use must have a verified integration before the feature is complete; a GHCR-only milestone does not satisfy completion.

- Q: Should applications submit their own database queries or invoke only predefined operations? → A: Adopt project-scoped queries through the protected service. The service maps each verified caller to an explicitly restricted database role; the database enforces its permissions. Backend credentials stay inside trusted execution, and administration and migrations use separately authorized bindings.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Manage Secrets Privately (Priority: P1)

As a platform operator, I want centrally managed credentials and operation permissions so that applications can perform approved work without receiving the credentials used to perform it.

**Why this priority**: Keeping backend credentials inside trusted execution is the defining security boundary of this feature.

**Independent Test**: An authorized operator registers and updates a synthetic credential, configures an allowed operation, and inspects version metadata; an application can invoke that operation but cannot retrieve the credential or manage its permissions.

**Acceptance Scenarios**:

1. **Given** an authenticated operator with management permission for a project, **When** they register a named credential and update its value, **Then** the service retains immutable versions, identifies the approved active version, and exposes only permitted metadata to ordinary management queries.
2. **Given** a project-scoped operator or caller, **When** they attempt to inspect, modify, use, or grant access to another project's credentials or platform credentials, **Then** access is denied without revealing credential values or names outside their scope.
3. **Given** a client without authorized private access, **When** they attempt to reach credential management, operation execution, health, or recovery functions, **Then** none is publicly accessible.
4. **Given** stored credentials, **When** vault processes are replaced, **Then** acknowledged versions, access grants, and operation definitions survive without reinitialization.
5. **Given** an application permitted to perform an operation, **When** it requests the raw credential or attempts to make an operation return backend authentication material, **Then** the request is denied and no backend credential is returned.

---

### User Story 2 - Execute Operations Without Delivering Credentials (Priority: P1)

As an authorized application or node, I want the vault service to complete a permitted operation on my behalf so that I receive the useful result without handling the backend credential.

**Why this priority**: Returning credentials, even temporarily in memory, does not satisfy the requested architecture.

**Independent Test**: Pull an authorized private GHCR image, exercise the database reads, writes, and transaction behavior required by two projects, and exercise each inventoried platform and external-service credential use through trusted execution. Verify correct results, cross-project denial, and absence of backend credentials in caller storage, responses, and instrumented caller processes.

**Acceptance Scenarios**:

1. **Given** a registered caller, approved operation, permitted target, and usable credential, **When** the caller submits valid input, **Then** the service authorizes the request, uses the credential internally, completes the operation, and returns only the allowed result and non-sensitive status.
2. **Given** denied access, an unknown operation, an unsupported target, missing credential, or an unavailable or locked vault, **When** an operation is requested, **Then** it fails closed with a non-sensitive reason and does not fall back to giving credentials to the caller or allowing a direct credential-based connection.
3. **Given** a node authorized to pull a particular private GHCR image by immutable digest, **When** its container runtime requests that image through the configured integration, **Then** trusted execution authenticates to GHCR and returns the matching image contents without returning a GHCR credential or a reusable upstream authorization token. An unauthorized image request is denied.
4. **Given** an existing credential used directly by a project or platform component, **When** that consumer migrates, **Then** its required operations are verified through the new service, its former credential copies are removed, and exposed legacy credentials are invalidated at their issuer before cutover is declared complete.
5. **Given** a clean environment with no working application identity service or private image access, **When** an operator follows bootstrap instructions, **Then** the vault service and its required operation integrations start without a circular dependency on the service being bootstrapped.
6. **Given** a new integration requirement, **When** it is evaluated for onboarding, **Then** the operator can identify its supported operations, targets, result format, permissions, and required changes to cluster configuration, project deployment, or application code. Unsupported operations remain unavailable until an integration is implemented and verified.
7. **Given** a caller identity token, **When** it is used to request an operation, **Then** only an authentic, unexpired token from a trusted issuer and intended for this service can establish identity, and current permissions must independently allow the operation and target. Expired, forged, wrong-service, or revoked access is denied; tokens do not enable direct GHCR or database authentication.
8. **Given** two projects with separate restricted database roles, **When** each submits its own permitted queries and transactions through trusted execution, **Then** the service maps the verified caller to its approved role, the database enforces that role's permissions, the application receives results without backend credentials, and required transaction behavior is preserved. Attempts to access peer-project, identity-provider, or administrative data, or to select a more privileged role, are denied.
9. **Given** a platform or project operation using another inventoried backend credential, **When** the caller performs the operation through its approved integration, **Then** its required behavior is preserved while the backend credential stays inside trusted execution. Verification covers identity-provider access, gateway client authentication and signing, credential-dependent administration and provisioning, and each existing external-service API use present in the inventory.
10. **Given** the complete credential-use inventory, **When** feature completion is evaluated, **Then** every entry has a verified integration, verified rotation/revocation behavior, and completed removal and invalidation of legacy caller-side credentials. Any unresolved entry blocks feature completion; image pulling alone cannot satisfy this gate.
11. **Given** an application role with read-only access to an approved table and no administrative privileges, **When** it submits an allowed read, a write, a permission change, or access to an ungranted table, **Then** only the allowed read succeeds. Separately authorized administration and migration requests use their own bindings.
12. **Given** a caller with an established database connection, **When** its operation grant is revoked, **Then** its next database operation is denied through that connection as well as through a new connection; an earlier successful login does not preserve revoked permission. Handling already executing statements and transactions remains explicitly documented per integration.

### User Story 3 - Rotate and Revoke Credentials Deliberately (Priority: P2)

As a platform operator, I want explicit credential-version and integration-adoption state so that rotation and revocation change what trusted execution actually uses.

**Why this priority**: Updating the stored value alone does not prove that an integration or an existing upstream connection stopped using an old credential.

**Independent Test**: Stage a synthetic replacement, verify adoption by the affected operation integration, simulate failed adoption, and complete issuer-side invalidation of the previous credential.

**Acceptance Scenarios**:

1. **Given** an active credential and registered operation bindings, **When** an operator stages a replacement, **Then** the previous version remains identifiable and each affected binding's selected and verified-active version is visible without exposing values.
2. **Given** a replacement that an integration cannot use, **When** its adoption check fails, **Then** rotation is reported incomplete; the previously approved version may remain active only while it is neither revoked nor declared compromised.
3. **Given** a revoked caller access grant, **When** that caller makes its next operation request, **Then** authorization is denied even if it holds a previously issued identity token. Revocation does not claim to recall already returned results or undo completed external effects.
4. **Given** a compromised backend credential, **When** revocation starts, **Then** new operations cannot use that version; completion requires verified issuer-side invalidation and the documented disposition of upstream sessions and in-flight operations that used it.
5. **Given** concurrent edits based on the same version, **When** one succeeds, **Then** the other reports a conflict rather than overwriting the successful update.

---

### User Story 4 - Audit and Recover the Vault (Priority: P2)

As a platform operator, I want attributable operations and recoverable protected backups so that I can investigate misuse and recover trusted execution after storage loss.

**Why this priority**: The service centralizes credentials and becomes a dependency of the operations it performs.

**Independent Test**: Exercise allowed and denied synthetic requests, inspect audit records for attribution and absence of credentials, and restore a protected backup into a clean environment using separately held recovery material.

**Acceptance Scenarios**:

1. **Given** successful and denied management requests, operation requests, permission changes, and recovery actions, **When** a reviewer examines audit records, **Then** each identifies actor, time, operation, permitted target metadata, request identifier, and outcome without containing credentials or sensitive request/result payloads.
2. **Given** that a request's audit event cannot be durably recorded, **When** execution is requested, **Then** the service refuses to begin the external operation. If an external effect occurred before a later failure, the service does not falsely claim that it was undone.
3. **Given** loss of vault storage, **When** an operator restores a backup with separately held recovery material, **Then** versions, grants, and operation definitions match that backup; execution stays disabled until access and revocation records have been reconciled.
4. **Given** a backup without authorized recovery material, **When** an unauthorized party examines it, **Then** backend credentials cannot be recovered in plaintext.
5. **Given** a candidate service deployment, **When** measured resource requirements exceed available capacity or reduce protected allocations, **Then** deployment is rejected before it affects running projects.

### Edge Cases

- A locked, uninitialized, or unreachable vault denies new credential-dependent operations. Callers receive no emergency credential copy. Already returned results, cached images, and completed external effects may remain usable and are not recalled by vault unavailability.
- A request can fail after an upstream operation has taken effect. Integrations must distinguish confirmed success, confirmed failure, and unknown outcome, and must document safe retry behavior. Non-repeatable operations must not be blindly retried.
- A caller may try to turn the service into an unrestricted proxy by supplying arbitrary targets, redirects, commands, or credential identifiers. Only explicitly authorized targets and operations may execute; redirects and result handling must not expose upstream authentication material.
- Results can themselves be sensitive. Access to result data is authorized separately from the fact that the service holds a credential; logs must not record sensitive payloads. Image contents are an intended result, but release images must not embed backend credentials.
- Long-running operations and established upstream connections need explicit timeout and revocation behavior. Revoking a grant prevents the next request; handling already accepted work is defined per integration and must be observable.
- A failed or stalled image transfer must not expose authentication headers or upstream tokens. Image digests must be verified, and cached images remain subject to the integration's authorization policy when served.
- Permanent deletion requires explicit confirmation of affected operation bindings; active integrations must not be silently orphaned.
- Restoring an older backup may reintroduce obsolete grants or credentials. Execution remains disabled until reconciliation finishes.
- Recovery must work without the original cluster, application identity service, or private image access that depends on the failed vault service. Bootstrap images and recovery dependencies need an independently usable path.
- Recovery material lost together with vault storage makes recovery impossible; separate custody must be verified before recovery readiness is declared.
- A consumer with no compatible operation integration cannot silently revert to raw credential delivery and cannot be marked migrated.
- Reused database connections must not carry another caller's effective role, authorization context, or unfinished transaction into a new request. Identity-token expiration or access revocation must be checked for subsequent operations; login-time authentication alone does not satisfy the next-operation denial requirement. A valid query may still expose all data granted to its project role, so business-level user authorization remains required.
- A stolen caller identity token may enable permitted requests until expiration or access revocation. It must not widen the caller's scope or reveal backend credentials. Expiration without successful renewal denies subsequent requests; it never triggers an unauthenticated fallback. Audit records contain the verified caller identity rather than the token value.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The platform MUST operate an established vault product under organizational control and provide integrations that perform authorized operations with its managed credentials. A custom vault security engine remains out of scope; product-native capabilities, existing integrations, or narrowly scoped integration code may supply execution behavior. Acceptance: Stories 1 and 2, with each integration's responsibility documented.
- **FR-002**: The vault MUST support named credentials, explicit project or platform ownership, immutable value versions, and an identifiable approved active version. Stale concurrent updates MUST be rejected. Acceptance: Stories 1.1 and 3.5.
- **FR-003**: Management and operation access MUST require verified caller identity and explicit action-and-scope grants, deny access by default, and distinguish credential management, operation invocation, and permission management. Callers MUST NOT inherit platform-wide access merely by running inside the cluster. Callers MAY hold short-lived identity tokens restricted to this protected service. Each request MUST validate the token's authenticity, trusted issuer, intended service, and expiry, then check the caller's current operation and target permissions. Identity tokens MUST NOT grant direct access to backend systems, raw backend credentials, or additional Kubernetes API privileges. Acceptance: Stories 1.2, 1.5, 2.7, and 3.3.
- **FR-004**: Credential management, operation execution, health, and recovery functions MUST be private and MUST NOT be exposed through public ingress. Acceptance: Story 1.3.
- **FR-005**: Backend credentials MUST remain within the approved trusted execution boundary during use and MUST be encrypted in persistent storage, backups, and transit. They MUST NOT be delivered to caller nodes or project pods, including through Kubernetes Secrets or other control-plane objects, response bodies or headers, redirects, files, environment variables, logs, or process memory. Credential-bearing backups and provisioning material MUST remain outside caller storage. Acceptance: Stories 1.5 and 2.1–2.3 plus SC-005. The vault service is one logical trusted service; its internal process count does not relax credential confinement.
- **FR-006**: Acknowledged credential versions, ownership, grants, and operation definitions MUST survive ordinary process replacement without reinitialization. Acceptance: Story 1.4.
- **FR-007**: Each operation binding MUST declare its permitted caller scope, operation, target, input constraints, result contract, and internal credential reference. Execution MUST return only the authorized result and MUST NOT expose a raw-credential retrieval path to callers. Acceptance: Stories 1.5 and 2.1–2.2 and the unrestricted-proxy edge case.
- **FR-008**: Execution MUST fail closed on denied access, missing or revoked credentials, unsupported operations, and unavailable vault state. Integrations MUST report non-sensitive failure reasons and define timeout, cancellation, concurrency limits, and safe retry behavior; an unknown external outcome MUST NOT be reported as confirmed success or safely retried without supporting guarantees. Acceptance: Story 2.2 and the uncertain-outcome and long-running-operation edge cases.
- **FR-009**: Operators MUST be able to stage versions and identify affected bindings, with stored, selected, verified-active, and revoked states distinguished. Rotation MUST remain incomplete until affected integrations have verified adoption and required issuer-side invalidation is confirmed. Acceptance: Stories 3.1–3.2 and 3.4.
- **FR-010**: Caller-grant revocation MUST deny the next operation request, including requests authenticated with previously issued identity tokens. Backend-credential revocation MUST prevent new use of the revoked version and track issuer invalidation and affected upstream sessions separately. Acceptance: Stories 3.3–3.4.
- **FR-011**: Permanent deletion MUST require explicit authorized confirmation of affected operation bindings and produce an audit record. Acceptance: the active-binding deletion edge case.
- **FR-012**: Management, execution, permission changes, and bootstrap or recovery actions MUST have durable audit records containing actor, timestamp, permitted target metadata, request identifier, and outcome without credentials or sensitive payloads. The service MUST record an authorized execution attempt before an external effect, record the outcome when known, and support reconciliation of interrupted attempts without claiming atomic rollback of external systems. Acceptance: Stories 4.1–4.2 and the uncertain-outcome edge case.
- **FR-013**: The service MUST support protected backups and documented clean-environment restoration of versions, grants, and operation definitions. Recovery material MUST be held independently of the vault and its storage. A successful restore exercise MUST precede recovery readiness. Acceptance: Stories 4.3–4.4.
- **FR-014**: Restoration MUST keep operation execution disabled until access grants and revoked versions are reconciled against the independently held recovery record. Acceptance: Story 4.3.
- **FR-015**: Bootstrap and recovery MUST work without a functioning application identity service or credentials obtainable only through the uninitialized or lost service, including its private image-pull path. Routine operation MUST NOT retain unrestricted bootstrap access. Acceptance: Story 2.5, recovery in a clean environment, and denial of reuse of initial unrestricted access after bootstrap.
- **FR-016**: The first release MUST inventory and integrate every existing platform and project backend credential use, including GHCR, database access, identity-provider and gateway duties, and other existing external-service uses. The inventory MUST identify owner, consumer, required operations and targets, credential references without values, integration, and acceptance evidence. Temporary blockers may be tracked during implementation but MUST be resolved before feature completion; credential uses MUST NOT be silently removed from scope. Cutover MUST verify consumer behavior, remove obsolete caller-side copies, invalidate exposed legacy credentials, and retain exactly one authoritative management procedure. Acceptance: Stories 2.4, 2.6, and 2.10.
- **FR-017**: Trusted execution and its integrations MUST fit measured resource budgets without violating project isolation, protected reservations, or the memory-limit freeze. Feature adoption MAY require cluster/runtime configuration, deployment changes, and application integration code; Kubernetes source modification is not an assumed requirement. After integration, moving between supported environment profiles MUST remain configurable without environment-specific application code. Acceptance: Stories 2.6 and 4.5 and the migration inventory's change assessment.
- **FR-018**: The initial operation set MUST include pulling an authorized private GHCR image by immutable digest. GHCR authentication and transfer handling MUST occur within approved trusted execution; nodes MUST receive image contents without GHCR credentials or reusable upstream authorization tokens. A mechanism that merely returns image-pull credentials to a node does not satisfy this requirement. Acceptance: Story 2.3, including denied image access, failed transfers, and digest verification.
- **FR-019**: Each integration MUST document and verify which components can see credentials, how callers are authenticated, how targets and results are restricted, and which upstream protocol capabilities are required. A helper, sidecar, node plugin, or proxy outside the approved trusted execution boundary MUST NOT receive backend credentials. Acceptance: review each integration's data flow and exercise allowed, cross-project, forbidden-target, and credential-disclosure requests before onboarding.

- **FR-020**: Project applications MUST be able to submit their own database queries through the protected service under explicitly restricted per-project database roles. The service MUST map verified caller identity to an approved database and role; caller-supplied database or role names MUST NOT widen that binding. The database MUST enforce explicitly granted resources and actions, and normal application roles MUST NOT have ownership, permission-management, or administrative privileges. Backend database credentials MUST remain inside trusted execution. Integrations MUST preserve required reads, writes, transaction commit/rollback behavior, and caller-visible errors; project requests MUST NOT reach peer-project, identity-provider, or administrative data. Administration, provisioning, and schema migrations MUST use separately authorized operational bindings. Current authorization MUST apply to the next database operation even on established connections. Acceptance: Stories 2.8 and 2.11–2.12 and each consumer's functional and permission-denial checks.
- **FR-021**: Trusted execution MUST support every remaining inventoried backend credential use, including existing identity-provider administration and client provisioning, session-revocation duties, gateway client authentication, gateway signing or verification using secret keys, and existing external-service API operations. Existing separation between operational duties MUST be preserved. Public verification material and approved caller/user identity tokens are distinct from protected backend secrets; a backend credential MUST NOT be relabeled as a result or caller token to bypass confinement. Unsupported upstream behavior MUST be recorded as a blocking integration issue. Acceptance: Stories 2.9–2.10, with a success, denial, credential-confinement, and rotation/revocation check for each inventory entry.

### Key Entities

- **Backend Credential**: A password, API token, registry credential, or private cryptographic key used internally to perform an upstream operation. It is never an operation result delivered to a caller.
- **Credential Version**: An immutable revision with creation time, creator, and eligibility for internal use.
- **Caller**: A project application or platform/node duty requesting an operation, associated with an independently verified identity and explicit scope. Node membership alone is not authorization.
- **Caller Identity Token**: A short-lived credential held by an application or node to prove its identity to the protected service. It has a trusted issuer, caller identifier, intended service, and expiry; current access grants determine permitted operations and targets. It grants no direct backend access and may exist in protected caller runtime storage. It must never appear in source control, images, audit records, or operational logs.
- **Trusted Execution Boundary**: The protected environment containing the logical vault service and its internal credential-handling execution and storage components. One process or several internal processes may implement the service; all must remain outside caller environments. Declaring a component trusted does not authorize placing credentials on caller nodes.
- **Operation Integration**: A capability that understands an upstream service or protocol and performs an approved operation internally. One integration may support many credential bindings; arbitrary application code is not automatically admitted.
- **Credential-Use Inventory Entry**: A value-free record of an existing backend credential use, its owner and consumer, required operations and targets, approved integration, migration state, blockers, and acceptance evidence. One credential used by multiple consumers requires coverage of every use; registering its value alone is not integration.
- **Operation Binding**: An approved association among callers, permitted operations, targets, input/result constraints, and an internal credential, with selected and verified-active versions.
- **Access Grant**: Revocable permission for an authenticated identity to manage a scope or invoke specified operations, without implicit permission to retrieve backend credentials.
- **Operation Result**: Authorized data or status returned to the caller, such as image contents or a signature, excluding backend credentials and reusable upstream authorization material.
- **Audit Event**: An attributable record of an attempted operation and its outcome, excluding credentials and sensitive payloads.
- **Recovery Set**: Protected backup, independently held recovery material, and access/revocation records needed to restore safely.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: An authorized operator can register a synthetic credential and enable one preconfigured operation binding within 10 minutes using the documented procedure, without copying that credential to caller environments or source control. Creating a new integration is outside this timing target.
- **SC-002**: All unauthorized cases in an acceptance matrix covering unauthenticated, wrong-project, wrong-operation, forbidden-target, expired-token, forged-token, wrong-service-token, revoked, and raw-credential requests deny access; no unauthorized values or credential names are disclosed.
- **SC-003**: At feature completion, 100% of inventoried existing backend credential uses have verified integrations and zero unresolved migration blockers. Every consumer passes its required functional checks, no active legacy credential copies remain at callers, and each credential has exactly one authoritative management procedure. GHCR, databases, identity-provider and gateway duties, and all other inventoried uses are included in this completion gate.
- **SC-004**: Rotation exercises identify the active version for every affected binding, keep failed adoption visible, prevent new use of revoked versions, and demonstrate issuer rejection of the old credential and documented handling of existing upstream sessions.
- **SC-005**: Inspection of caller control-plane storage, files, environments, request/response captures, release artifacts, logs, and instrumented caller-process memory finds zero occurrences of synthetic backend credentials during successful and failed representative operations. Every exercised request has attributable audit evidence. These checks demonstrate the tested paths; they do not assert immunity to compromise of trusted execution or credential issuers.
- **SC-006**: Process replacement preserves 100% of acknowledged synthetic versions, grants, and operation definitions. A clean-environment restore reproduces the selected backup, with obsolete access reconciled before execution resumes. Restore duration and backup age are recorded; no numerical recovery-time or data-loss limit has been accepted yet.
- **SC-007**: An operator completes documented bootstrap, rotation, and recovery exercises without undocumented assistance and identifies the active credential version of each exercised binding without seeing its value.
- **SC-008**: A representative node pulls an allowed private GHCR image with the expected digest through trusted execution, receives no GHCR credential or reusable upstream authorization token, and is denied an unauthorized image. Bootstrap succeeds without relying on that same image-pull service before it is running.

- **SC-009**: Two representative project database integrations pass their permitted query and commit/rollback exercises and reject every tested ungranted action, peer-project access, role escalation, and administrative request. A read-only binding rejects writes; a revoked caller cannot issue its next operation through an existing connection. Every remaining platform or project inventory entry passes its defined success, denial, credential-confinement, and rotation/revocation checks. None exposes backend credentials to caller environments.

## Assumptions

- “Vault service” names the proposed credential-management and authorized-operation capability. An established vault product may supply only part of that capability. Selecting an established product does not imply that it can execute arbitrary database or external API operations without integration work.
- Initial scope includes all existing backend credential uses of the cluster's platform and projects. Required integrations include private GHCR image pulls; project and platform database access and provisioning; identity-provider administration and client operations; gateway client authentication and secret-key signing or verification; and other existing external-service API uses identified by inventory. Each must be implemented and verified within this feature. Future unrelated service integrations are outside this inventory-based release boundary. Automatic backend credential issuance, certificate-authority services, and a general-purpose cryptographic catalog beyond existing required key uses are not assumed requirements.
- Caller environments include application nodes, project pods, and their control-plane storage. Credential-handling execution and storage must be isolated from those environments. Placement, required additional infrastructure, and its cost must be assessed against this boundary; a sidecar on a caller node does not satisfy it. This specification does not claim protection against an administrator controlling the trusted service's own host or an upstream credential issuer.
- Caller authentication uses short-lived identity tokens held by applications or nodes, with narrowly scoped permissions checked on every operation request. This is an explicit allowance for caller identity tokens only; backend credential confinement remains mandatory. Token issuer, issuance and renewal procedures, maximum lifetime, and protected runtime storage mechanism are implementation-planning decisions. The plan must document finite expiry and verify denial of expired, forged, wrong-service, and revoked access; approval of this model does not automatically authorize project ServiceAccount token mounts.
- The vault and any internal operation helpers constitute one logical trusted service. Internal process decomposition is an implementation-planning decision, not a separate user-facing security requirement. All credential-handling components must stay inside the protected environment and outside application nodes and project pods; callers receive only authorized results.
- Ratified Constitution v1.3.0 is the authoritative deployment governance baseline. Principle V formally mandates centralized Vault operation and zero plaintext secrets, superseding legacy Kubernetes Secret delivery. Principle II's prohibition on project ServiceAccount tokens remains binding, satisfied via short-lived caller identity tokens verified by the platform identity boundary rather than Kubernetes API access. Principle VI's environmental portability across local K3s, VPS K3s, and managed Kubernetes remains mandatory.
- Cluster and runtime configuration can route supported operations through trusted execution; compatible proxies may reduce project code changes. New operation interfaces may require application changes. Neither universal drop-in compatibility nor changes to Kubernetes source code are assumed.
- Database integration uses the accepted project-scoped query model. Projects retain query construction and business authorization; caller identity authorizes the project and does not automatically establish the permissions of each end user. Applications must use safe parameter binding for untrusted values and enforce user-level data access, with database row policies where required. Normal runtime grants cover only needed resources and actions; schema migration privileges remain separately controlled. Proxy product and protocol details belong to planning, and no product is assumed to satisfy per-operation revocation without verification.
- Private GHCR image pulling occurs before the application starts and must be integrated with the node's image-pull path. An application helper that starts only after its image is pulled cannot solve that bootstrap dependency.
- No numerical availability or recovery objective was selected in this discussion. Multi-node high availability is not an assumed requirement, and dependent operations may be unavailable during service failure or recovery. Integration-specific timeout, concurrency, transfer, and capacity limits belong in the implementation plan with measurable acceptance checks.
- Operators have authorized private access and independent provisioning, issuer-revocation, and recovery procedures. Provisioning and recovery are privileged paths separate from ordinary caller operations; they must not use application nodes as credential staging locations.
- Backups remain required for tested recovery. Scheduling and audit retention follow an explicit operator-selected policy; the existing optional scheduling baseline is daily at 00:00 UTC with seven-day retention. The earlier proposed 24-hour data-loss and four-hour restore targets were not accepted and are not requirements.
