Visitor & Platform Impact

Zero Spot nodes sit on the request, OIDC verification, or database path. Every login, session check, and DB query executes on On-Demand Node 1.

Why 1 Frontend + 1 Backend Pod (Not 2 Replicas)?

proj-pn and proj-health run replicas: 1 of two separate tiers: a web UI container (frontend) and an API server (backend). proj-blog is static HTML only (1 pod).

Splitting UI from API enforces zero-trust NetworkPolicy (the frontend pod cannot touch PostgreSQL or Vault proxies) and lets UI updates deploy without restarting the API.

Simulator C: Why Does GKE Ever Reboot an On-Demand Node?

On-Demand VMs are never preempted for cheap capacity, but Google still patches the Linux kernel & Kubernetes kubelet against security CVEs during scheduled maintenance (and OpenBao can restart on any pod update).

Without Cloud KMS auto-unseal, a 3 AM security reboot leaves OpenBao locked ("sealed") until you wake up and type keys. With KMS, OpenBao unlocks itself in ~2s automatically.

Simulator D: Fluent Bit "Bookmark + Disk Outbox"

1 USB stick (RWO PVC) cannot plug into 2 nodes at once. Instead, each node uses a folder on its own boot disk (/var/lib/fluent-bit-state):

  • Bookmark (tail.db): Remembers the exact log line read (e.g. line #500) so pod restarts never skip or duplicate lines.
  • Outbox (/state/chunks, max 256 MiB): Saves unsent logs to disk (not RAM) while OCI internet is down, then sends them when it recovers.

2. Public GAR Digest Portability

Authorizes immutable @sha256:... image pulls from publicly readable Google Artifact Registry (GAR) alongside GHCR, retiring vault-registry-proxy with zero K8s pull secrets.

3. Keyless Cloud KMS Seal Wrapper

Permits openbao-0 to wrap its master seal key with GCP Cloud KMS (gcpckms) via keyless GKE Workload Identity so planned node upgrades unseal unattended.
