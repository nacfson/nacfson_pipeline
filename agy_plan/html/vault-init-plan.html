1. What is "Vault Init" and Why is It Required?

In OpenBao / HashiCorp Vault architecture, initialization and unsealing are two foundational, security-critical lifecycle events:

  • Storage Barrier Initialization (init): When an OpenBao pod starts with fresh, unformatted persistent storage (mounted at /var/lib/openbao/data via PVC data-openbao-0), it has no cryptographic barrier. Running init generates the master encryption key used to encrypt all persistent secrets at rest, splits this master key into Shamir secret shares (the Unseal Keys), and issues an initial high-privilege Root Token.
  • Unsealing (unseal): Initialization puts the master key into Shamir shares and immediately discards the master key from memory. Vault remains in a SEALED state. In this state, Vault cannot read or write data, and its HTTP readiness endpoint responds with HTTP 501 (uninitialized) or HTTP 503 (sealed). Feeding the required threshold of unseal keys reconstructs the master key in RAM, opening the barrier and returning HTTP 200 OK.
Why GitOps Cannot Auto-Initialize Vault Secrets
Per Constitution Principle V (Decoupled Secret Governance): "The unseal key is NEVER stored within Git or cluster-local unencrypted storage. Git contains declarative intent, but runtime cryptographic roots belong strictly to out-of-band operator custody." Automatic unseal requires either a cloud KMS (e.g. AWS KMS, OCI Vault KMS) or manual operator submission.

3. Step-by-Step Implementation Details

Step 1: Check Pod Health & Status Diagnostics

Verify that openbao-0 is running and inspect its initialization status via the Vault API.

kubectl exec -n vault openbao-0 -- env VAULT_ADDR="http://127.0.0.1:8200" bao status -format=json

Expected return: "initialized": false, "sealed": true, exit code 2 (uninitialized).

Step 2: Execute Operator Init Cryptographic Barrier

Run operator initialization with Shamir parameters (1 share, threshold 1 for single-node development):

kubectl exec -n vault openbao-0 -- env VAULT_ADDR="http://127.0.0.1:8200" \
  bao operator init -key-shares=1 -key-threshold=1 -format=json

This outputs the Base64 unseal key (unseal_keys_b64[0]) and the root token (root_token).

Step 3: Unseal the Vault Master Key Decryption

Submit the unseal key to decrypt the barrier:

kubectl exec -n vault openbao-0 -- env VAULT_ADDR="http://127.0.0.1:8200" \
  bao operator unseal "$UNSEAL_KEY"

Immediate effect: sealed: false, readiness probe passes, pod status transitions to 1/1 Running.

Step 4: Enable Secrets Engines & RBAC Policies Mounting & ACL 

# Enable KV v2 engine for versioned platform credentials
kubectl exec -n vault openbao-0 -- env VAULT_ADDR="http://127.0.0.1:8200" VAULT_TOKEN="$ROOT_TOKEN" \
  bao secrets enable -version=2 kv

# Enable transit engine for cryptographic signing / HMAC
kubectl exec -n vault openbao-0 -- env VAULT_ADDR="http://127.0.0.1:8200" VAULT_TOKEN="$ROOT_TOKEN" \
  bao secrets enable transit

# Enable file audit logging to /var/log/openbao/audit.log
kubectl exec -n vault openbao-0 -- env VAULT_ADDR="http://127.0.0.1:8200" VAULT_TOKEN="$ROOT_TOKEN" \
  bao audit enable file file_path=/var/log/openbao/audit.log log_raw=false

# Apply policies from deploy/platform/vault/policies/
for f in deploy/platform/vault/policies/*.hcl; do
  pname=$(basename "$f" .hcl)
  kubectl exec -i -n vault openbao-0 -- env VAULT_ADDR="http://127.0.0.1:8200" VAULT_TOKEN="$ROOT_TOKEN" \
    bao policy write "$pname" - < "$f"
done

Per Spec 002 FR-015, unrestricted bootstrap root access must be revoked once services operate with AppRoles and delegated credentials: 

kubectl exec -n vault openbao-0 -- env VAULT_ADDR="http://127.0.0.1:8200" VAULT_TOKEN="$ROOT_TOKEN" \
  bao token revoke -self

4. How We Can Execute This Now

There are two recommended execution approaches:

Option A: Automated via Repository Scripts (Recommended)

We run the pre-built scripts from the repository directly. Because the workstation's local kubeconfig and policies directory are present, we can establish an SSH tunnel or invoke the commands cleanly: 

# 1. Update local kubeconfig certificates from oracleCloud
ssh oracleCloud "cat ~/.kube/config" > ~/.kube/config
sed -i 's/127.0.0.1:6443/oracle-free:6443/' ~/.kube/config # Or forward port

# 2. Run automated vault-init.sh
./scripts/vault-init.sh

# 3. Run automated vault-seed-inventory.sh
VAULT_TOKEN="<ROOT_TOKEN>" ./scripts/vault-seed-inventory.sh

Option B: Break-Glass Execution Directly via SSH on the Node

We execute the exact steps over SSH directly on oracleCloud using kubectl exec. This ensures zero network tunnel dependency: 

ssh oracleCloud '
  # Run operator init inside openbao-0
  kubectl exec -n vault openbao-0 -- bao operator init -key-shares=1 -key-threshold=1 -format=json
'
