Vault + Internal Keycloak/Gateway + Zero-Secret Project Auth

Vault Holds 100% API Keys Projects Hold 0 Secrets / 0 Configs

OpenBao Vault holds all Google OAuth & signing secrets · Keycloak/Gateway is the internal Google OAuth intermediate · Projects only call internal HTTP to verify auth

1. OpenBao Cluster Vault (ns: vault) 100% of Secrets

Holds all API keys & credentials: identity/google-oauth (Google Client ID & Secret), gateway/hmac-secret, gateway/client-secret, and database/*.

2. Keycloak + Gateway (ns: identity) Google OAuth Intermediate

Fetches Google OAuth keys from Vault on startup, orchestrates headless Google OAuth (kc_idp_hint=google, zero Keycloak login UI), and exposes internal HTTP verification (gateway.identity.svc:8080).

3. Hosted Projects (ns: proj-pn, etc.) 0 Secrets · 0 OAuth Config

Holds zero secrets, zero Google API keys, and zero Keycloak/JWKS URLs. Only calls http://gateway.identity.svc:8080/auth over internal cluster HTTP to verify user identity.

TARGET ARCHITECTURE Vault Holds All Keys · Keycloak Brokers Google Invisibly · Projects Only Call Internal Gateway HTTP to Verify Auth

Projects do not verify Keycloak JWTs or fetch JWKS keys (/realms/platform/* removed from projects). pn-backend only calls http://gateway.identity.svc:8080 (/auth/exchange, /auth, /auth/logout).

Strict Separation of Concerns

          

            

              
🏦 OpenBao Vault: Holds All Secrets

              
Stores Google OAuth Client ID/Secret, Gateway AES/HMAC keys, and DB passwords. Projects hold 0 secrets.

            

            

              
🏛️ Keycloak + Gateway: Google OAuth Intermediate

              
Redirects straight to Google (kc_idp_hint=google), exchanges tokens, and seals sessions. Never shows a Keycloak login UI.

            

            

              
⚙️ Projects (proj-pn): Verify-Only HTTP Client

              
Zero Keycloak URLs, zero JWKS keys, zero JWT parsing. Only calls http://gateway.identity.svc:8080/auth to verify identity.

          WHY LIVE CLUSTER FAILED TODAY
          2 Concrete Causes Fixed by This Change
        

        

          

            
Cause #1: Stale gateway:latest Pod in vps-k3s

            

              deploy/platform/identity/gateway-deployment.yaml used a floating tag (image: ghcr.io/nacfson/platform-auth-gateway:latest). When Spec 009 merged, the YAML file had no diff, so FluxCD never restarted the pod. The live cluster is still running the old Gateway binary that redirects to /realms/platform/protocol/openid-connect/auth without kc_idp_hint=google, causing Keycloak to render its username/password login form!
            

          

          

            
Cause #2: Project Backend Still Configured with Keycloak URLs & JWKS

            

              deploy/projects/pn/workloads/backend-deployment.yaml still injected AUTH_JWT_JWKS_URL, CENTRAL_AUTH_INTERNAL_URL, and CENTRAL_AUTH_URL into pn-backend, and Project_PN's auth_middleware.go still called verifier.Verify() against Keycloak's JWKS endpoint even after gateway.ConfirmSessionHandle() already verified the session with gateway.identity.svc:8080/auth!
